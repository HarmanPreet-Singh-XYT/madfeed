# Workflow Taste

- Does not want `Co-authored-by` trailers in commits; wants the co-authored attribution removed. Confidence: 0.85
- Expects a feature to be carried across every surface it touches, not just the one page named in the request — e.g. when CRUD lands on a list page, the matching detail page should get the same treatment without being asked, and "improve this flow" includes refining the page that hosts the new control, not just the control. Routinely follows up with a short "did you also do the detail page?" probe when a surface may have been left unpolished. Confidence: 0.82
- For UI redesign work, wants reference research done first and names the source explicitly ("use mobbin to research") — screens from established products so the layout follows proven patterns rather than being invented from scratch. Confidence: 0.75
- Prefers the full proposed scope implemented at once over a phased/P0-only subset — when offered a prioritized slice, expects the whole plan carried out in one pass (with clear reporting of anything genuinely deferred and why). Deadline pressure is explicitly not a reason to cut scope: when the assistant framed remaining work around the clock ("two hours left, record the video instead"), he waved the clock off ("don't worry about the clock… if u r building then build it fully") and wanted the feature finished properly. Confidence: 0.87
- Does not accept "deliberately not built" or "still open" as a resting state: when a report lists features skipped for lack of backend support, or a closing "still open, and why" section, expects those items actually closed out next ("cant you close the open stuff") rather than re-argued as deferred, and treats backend/schema/API work as in scope rather than something off-limits. Confidence: 0.88
- Pushes back on a narrow, deliberately single-purpose integration: when told a third-party API (Tavily) was wired into "one place only — deliberate", asked for more use cases "at more places", treating breadth of integration as a feature in its own right rather than accepting a minimal call site. When the assistant then ranked further call sites and recommended holding on one of them, he overrode it ("add third also, i mean build as much as u can") — so don't defend a small integration surface, and don't answer a "more places?" request with a ranked list of what to skip. Confidence: 0.75
- Treats any mention of "bugs" as a defect that must not ship: when a report lists bugs found, expects them fixed and verified rather than catalogued, and pushes back on the framing itself ("what bug i dont want to have bugs in the code") instead of accepting a list of known issues. Confidence: 0.62
- Weighs open-sourcing against commercial intent: states a standing goal of keeping proprietary work private in service of a SaaS path, and expects publishing under an OSS license to be treated as a deliberate, one-way business decision rather than default packaging — not something decided by a deadline or a contest rule. Confidence: 0.6
- Wants a project README treated as a complete, compelling document rather than a runbook: positioning that makes the project stand out, setup instructions, architecture, integrations, and "everything" — enumerates the sections rather than accepting a minimal quick-start. Also expects docs to be kept in sync with the code: adding an integration or feature is not done until the README (and any key-usage/env docs) explains how it is used, and he probes for it after the fact ("did u update readme on how we use the tavily", later just "did u update the readme") rather than asking up front. Expect the probe as a matter of course after any feature lands, and expect the answer to be an audit against what actually exists now — stale counts and missing deployment paths corrected — not "already covered". For an integrations section specifically, an on/off table is not enough: he wants each service described by what it does *in this product*, plus the integrations that are not built yet, each with how it would feed data in (and what works today as the workaround). Confidence: 0.8
- Deploys to their own VPS, and does not want config written for managed platforms: rejects Fly.io/Vercel-style deploy files ("dont write fly, i hv my own vps") and expects hosting artifacts to target the server they already run (compose + their existing nginx), not a PaaS. The frontend is the one exception — the web app is hosted on Vercel, so VPS deploy plans should cover only the backend services and they will correct scope ("web is deployed on vercel i dont need that for deployment on vps") rather than accept a full-stack compose/doc that provisions something already hosted elsewhere. Confidence: 0.82
- Expects database migrations applied to the hosted (Supabase) Postgres as well as the local stack, not just committed — probes after a schema-changing feature lands ("did u do migrations for supabase") and expects the answer to be verified against the live database (migration version, new columns/extensions) with local and hosted agreeing. Confidence: 0.6
- Treats seeded demo/sample data as a shipped deliverable, not scratch state: after a feature lands he probes whether it needs refreshing ("do you need to update the demo data") and expects the data a viewer will actually see to be current with the new feature, populated with real results rather than empty roll-ups, and scrubbed of the assistant's own test artifacts (duplicate uploads, stuck rows, mismatched lookups). Confidence: 0.6
- Works with other agents/writers concurrently in the same repo, so expects verification to separate own breakage from other people's in-flight changes — re-check the tree before and after edits, don't clobber or revert foreign edits, and report which failures originate elsewhere instead of silently "fixing" them. Confidence: 0.85
